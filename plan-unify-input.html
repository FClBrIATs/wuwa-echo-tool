入力モード一本化 — 実装計画

合計値入力を廃止し、項目別入力に統一する。既存の保存データを壊さないことを最優先に組んでいる。数値はすべてツール本体で実測した。

16移行が必要な入力項目
162影響を受けうるテスト
一致移行後のスコア（検算済み）

前提移行できることは確認済み

計画を立てる前に、両モードが同じ結果を出せるかを実測した。

合計値モードで入力したビルドを、自動加算される分を差し引いて項目別の「その他」欄へ移したところ、期待ダメージ指数が完全に一致した。

移行前  E = 9243 ／ 全体攻撃力 2600
移行後  E = 9243 ／ 全体攻撃力 2600   ← 一致
残差 16項目、マイナスなし
これが計画の土台になる。項目別モードは合計値モードの上位互換で、機能の後退なしに統合できる。

移行の式

項目別モードはハーモニー・武器・キャラ・音骸を自動で足す。合計値モードの入力にはそれらが既に含まれているため、単純にコピーすると二重計上になる。自動加算される分を引いた残りを「その他」に入れる。

その他 = 合計値モードの入力 − 項目別モードが自動計算する分

対象は16項目。基礎値・全体値・クリ率・クリダメ・属性ダメ6種・全属性ダメ・スキル別ダメ5種。

課題先に決めておくこと

実装前に判断が要る点。ここを飛ばすと後戻りする。

1. 残差がマイナスになる場合がある

ハーモニーなどの自動加算が、入力された合計を上回るケースが実際に起きる。実測例：

合計値モード： クリ率 20%
ハーモニー等の自動加算： 22%
→ その他 = −2%

合計値モードでは登録データを使わないので、「ハーモニーを選んでいるのに合計値には含めていない」という入力が成立していた。移行するとその矛盾が表面化する。

方針の候補：(a) マイナスのまま入れて計算を一致させる（数字は不自然だが結果は正しい）／(b) 0で止めて差分を警告する（数字は自然だがスコアが変わる）。
一致を優先するなら (a)。ただし「その他 −2%」という表示の意味を説明する必要がある。

2. 手軽さを失わないか

合計値モードは4項目を打つだけで使えた。項目別モードの編集可能な欄は52個ある（残り66個は自動計算の読み取り専用）。

ただし実際に必須なのは「その他」の4項目だけ。登録データが無くても、その他欄に直接打てば従来と同じ手数で使える。問題は導線で、「その他」という名前では「ここに全部打てばいい」と分からない。

3. 「その他」という名前が実態に合わなくなる

一本化後は、この欄が主要な直接入力欄になる。名前と配置の見直しが要る。

計画実装の順序

前の段が次の段の前提になっている。1〜2が終われば、既存ユーザーのデータは安全な状態になる。

  1. 移行処理を書く（UIは触らない） 保存データに合計値モードの入力があれば、起動時に残差を計算して「その他」へ移す。移行済みの目印を保存し、二重実行を防ぐ。この時点ではモード切替は残したまま、移行結果が元と一致することをテストで固める。
  2. 移行のテストを厚くする ハーモニーあり／なし、音骸あり／なし、残差がマイナスになる場合、空データ、壊れたデータ。ここが最も壊してはいけない部分なので、UIを消す前に検証を済ませる。
  3. 入力欄の名前と並びを直す 「その他」を直接入力の主役として扱えるようにする。項目別モードだけで違和感なく使えることを確認してから、次へ進む。
  4. 合計値モードのUIを外す モード切替ボタン、合計値ブロック、ダメバフ／スキルバフの合計値側を削除。setInputMode と切替の配線も外す。
  5. 計算側の分岐を落とす inputMode の32箇所、totalModeContribution（14行）、getHarmonyTotalEff ほか4つのラッパー、S.base_stat など合計値モード専用の状態を削除。スコア計算の総入れ替えではなく、分岐の片側を消すだけ。
  6. テストを項目別へ寄せる テストの共通ビルド定義が合計値モードの項目を使っているので、その1箇所を書き換える。162件が通ることを確認する。
  7. ドキュメント更新 README の機能一覧、PHASES.md に判断の記録。

確認したいこと

着手前に決めていただきたい点：

  • 残差がマイナスになったときの扱い — 計算の一致を優先するか、表示の自然さを優先するか
  • 「その他」欄の呼び方 — 「直接入力」「手入力」など。ここが一本化後の主役になる
  • 移行のタイミング — 起動時に黙って移すか、確認を出してから移すか
